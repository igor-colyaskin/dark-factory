## Ориентир

Довести DF до уровня, когда она сможет генерировать любые приложения
в рамках заданного бюджета, законности, доступности ресурсов.

Это **не цель**, а ориентир. Цель — навыки: научиться работать с командой
агентов, понять как устроен диалог человека и LLM, получить опыт
проектирования agent-систем.

Если v0.1 — велосипед, v0.2 — скутер, то v100.500 — самолёт.
Самолёт построить не получится (и не нужно — уже летают). Но каждый шаг
по маршруту оправдывает себя полученным опытом.

## Главный вектор: от workflow к agency

**Workflow (сейчас):** пользователь говорит → агенты выполняют → готово.
Агенты — руки без головы.

**Agency (цель):** агенты говорят "подожди" вместо "готово".
Спрашивают, предупреждают, проверяют, помнят.

Переход происходит в три стадии:
NEGOTIATE → REMEMBER → VERIFY
  v0.3        v0.5       v0.7

(v0.4 GitHub Integration — инфраструктурный шаг, открывает путь к REMEMBER)
(v0.6 Local Runner — инфраструктурный шаг, открывает путь к VERIFY)


Каждая стадия делает следующую мощнее:
- Negotiate без Verify = спросил правильно, сделал криво, не заметил
- Verify без Negotiate = проверил, но проверял не то
- Remember без Negotiate+Verify = помнит ошибки, но не умеет их не повторять

## Выпущенные версии

### v0.1 — Велосипед ✅
Pipeline работает. Агенты вызываются через OpenRouter. Результат — код
в workspace/. Учебная задача решена.

### v0.2 — Скутер ✅
Приложения деплоятся на Fly.io. Публичная ссылка, QR-код.
Получатель не ставит Docker/Node — достаточно браузера.

### v0.2.1 — Шасси ✅
Products page: архив всех созданных приложений. CRUD через UI.
App slug из текста заказа (первый микро-шаг agency).

### v0.3 — NEGOTIATE ✅
Архитектор останавливает конвейер и разговаривает с заказчиком.
Два режима: clarify (структурированные вопросы с вариантами ответов)
и spec (полная спецификация перед разработкой). Spec Review UI
с кнопками Start/Cancel. Developer prompt принимает spec напрямую.

Метрики dogfooding:
- Ясный заказ (Pomodoro): $0.12, 1 мин, 0 раундов вопросов
- Неоднозначный заказ (Habits): $0.18, 1:28, 1 раунд вопросов

### v0.4 — GitHub Integration ✅
Код сгенерированных приложений автоматически пушится в GitHub-репо пользователя.
README.md и SPEC.md генерируются и коммитятся вместе с кодом. При удалении
приложения репо удаляется. Открывается путь к REMEMBER (v0.5).

Ключевые решения:
- GitHub Client — первая имплементация Source Storage контракта
- Поле `sourceUrl` (не `githubUrl`) — абстракция от конкретного бэкенда
- GITHUB_PUSH — non-blocking: если GitHub недоступен, заказ завершается с `sourceUrl: null`
- Delete non-blocking: Fly и GitHub чистятся best-effort, запись удаляется всегда
- Hyperspace LiteLLM (SAP internal proxy) вместо OpenRouter

### v0.5 — REMEMBER ✅
Архитектор использует прошлый заказ как baseline.

Режим A (Order by Reference): кнопка "Повторить с изменениями" на карточке →
префикс `На основе #N:` → `readApp` читает SPEC.md из GitHub → передаётся
архитектору целиком → архитектор применяет только дельту, без лишних вопросов.

Ключевые решения:
- `readApp(sourceUrl)` в `github-client.js` — читает SPEC.md по GitHub URL
- UI-кнопка, не текстовый парсинг — детерминированный триггер (Guided decisions)
- Весь spec передаётся целиком — spec маленький, вопрос не в объёме, а в поведении архитектора
- Prefix stripped в `generateUserPrompt` — агент видит только дельту пользователя
- Pattern Library (режим B) → Area-51
- Fly заблокирован на VDI → GITHUB_PUSH не тестировался end-to-end (блокер — решён в v0.6)

### v0.6 — Local Runner ✅
Fly.io заменён на локальный запуск. Полный pipeline работает на корп. VDI.

Каждое приложение сохраняется в `workspaces/{appName}/`. On-demand UX:
кнопка "Открыть" в Products стартует приложение и открывает `http://localhost:PORT`.
QR-код скрыт для localhost.

Ключевые решения:
- `local-runner.js`: копирует workspace, npm install, npm start, ждёт HTTP → возвращает `{ url, pid, port }`
- `process-registry.js`: in-memory реестр `{ appName → { pid, port } }` для teardown
- `executeLocalDeploy()` в оркестраторе — заменяет `executeDeploy()` (Fly) в реальном режиме
- On-demand UX, не постоянный URL — честная модель для localhost
- Нет Deployer facade — до появления второй реализации
- workspaces/ eviction → Area-51

### v0.6 — Local Runner

**Тема:** Deployer-контракт + Local Runner как первая имплементация.

**Триггер:** Fly.io недоступен на корп. VDI → Local Runner — production necessity,
не academic exercise. Разблокирует полный pipeline и открывает путь к VERIFY.

**Контракт (async-first):**
- `deploy(workspacePath, appName) → { url, pid, port }`
- `teardown(appName) → void`

**Workspace:** каждое приложение сохраняется в `workspaces/{appName}/`.
Все хранятся локально (кеш-стратегия — Area-51 до появления реальной проблемы).

**UX:** on-demand запуск. Кнопка "Открыть" в Products вместо постоянного URL.
Клик → старт → новая вкладка с `http://localhost:PORT`.

**Ключевое обучение:** проектирование interface по принципу
"контракт выводится из реальной потребности, не из спекуляции".

---

### v0.7 — VERIFY

**Тема:** агент проверяет свою работу глазами заказчика и отчитывается.

**A. Verification Report**
После запуска приложения агент-верификатор открывает `localhost:PORT` через
headless Chrome (puppeteer-core), делает скриншот, передаёт в vision-модель
вместе со spec. Выдаёт структурированный отчёт: что реализовано, что нет.

**B. Feedback Loop**
Пользователь видит отчёт и даёт точечную правку ("кнопки должны быть синими").
DF запускает доработку без полного пересоздания.

**Архитектура верификатора:**
Два модуля с единым контрактом `verify(url, spec) → Report`:
- **VerifierA** (структурный): HTTP-проверки, роуты, HTML — быстро, бесплатно
- **VerifierB** (визуальный): скриншот + vision LLM — медленнее, видит глазами заказчика

Запускаются последовательно (A → B) через модуль-композер.
Оркестратор вызывает один `verifier.run(url, spec)` и не знает о внутренней структуре.

Форма `Report` выводится из реализации VerifierA — не проектируется заранее.

**Ключевое обучение:** как агент оценивает собственную работу?
Как структурировать feedback, чтобы он был actionable?

### v0.8+ — CAPABILITIES (на зрелой agency-базе)

Расширение набора создаваемых приложений. Появляется **только когда
agency-слой достаточно зрел**, чтобы новые capabilities не ломали
качество.

Возможные направления:
- Telegram-каналы с автопубликацией
- Headless-сервисы (schedulers, scrapers)
- Multi-page приложения
- Внешние API-интеграции (с управлением secrets)

---

### v1.0 — горизонт

DF становится **осмысленным собеседником**: ведёт переговоры, предлагает
альтернативы, оценивает стоимость, согласует spec, отчитывается.

Не дата, а **состояние зрелости agency-слоя**.

## Принципы (напоминание)

1. **Agency over capabilities** — глубина переговоров важнее ширины умений
2. **Маленькие шаги ради понимания** — понял, прежде чем двигаться дальше
3. **Guided decisions over free-form** — варианты, а не пустое поле
4. **Не копим хвосты** — устаревшее удаляем

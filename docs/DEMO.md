# DF-IC Demo — заметки для питча

Аудитория: тимлид. Формат: показываю сам, в конце — "хочешь попробовать?".

---

## Ключевые тезисы

### DF-IC + Vibe coding = полный workflow

DF-IC покрывает воспроизводимые 80%: структура карточки, маппинг полей,
mock-данные, тесты, sandbox preview — за ~1 минуту вместо ~2 часов вручную.

Для оставшихся 20% — специфика команды, нестандартные паттерны,
индивидуальные требования — вайб-кодинг на готовом скаффолде работает
быстрее и надёжнее, чем пытаться описать всё это в промпте.
Это не ограничение — это дизайн-принцип: правильное разделение труда
между генерацией и кастомизацией.

## Pitch — draft-v1

### Позиционирование (категория, не фича)

DF-IC не предназначена для точечных задач и уникальных сценариев.
Её место — **воспроизводимая работа**: правильный ответ известен,
но руками его легко испортить из-за человеческого фактора.

> *«DF-IC делает так, чтобы правильный ответ не зависел от того,
> насколько внимательным ты был сегодня утром.»*

**Почему «правильный ответ», а не «не требующей ума»:**
детерминированная работа, а не творческая — точнее и без снисхождения к команде.

**Подкрепить конкретикой:** назвать один реальный инцидент —
например, карточки с неверным namespace из-за ручного клонирования.

```
5. Горизонт       «Сегодня — карточки. Паттерн
                   универсальный — завтра можно взять
                   что угодно с похожей структурой.»

6. Закрытие       «Попробуем на твоей следующей карточке?»
```

## Сценарии для демо

### Сценарий A — Generate с мокапом (primary, ~5 мин)

Реальная карточка из проекта, скриншот мокапа.
Пишем описание → запускаем → тимлид смотрит пайплайн → Preview в sandbox.

**Punch line:** *«Это заняло 90 секунд. Вручную — полтора часа.»*

**Риски:** LLM медленный / плохой результат → fallback (сценарий B).

### Что не показывать в питче

- Edit mode — слишком много контекста для первого показа
- Сравнение моделей (Gemini vs Claude) — это внутренняя задача, не для тимлида
- Import — не добавляет к основному message

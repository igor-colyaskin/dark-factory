# Dark Factory — Information Protocol

Правила работы с информацией в проекте. Цель: минимальный контекст при старте сессии,
отсутствие рассинхронов, единственный источник правды для каждого типа данных.

---

## Модель трёх температур

| Температура | Документы | Триггер пересмотра |
|-------------|-----------|-------------------|
| 🔥 HOT | `HANDOFF.md` | Каждая сессия — читать в начале, обновлять в конце |
| 🌤 WARM | `docs/backlog.md`, `docs/DEMO.md`, memory-файлы активной фичи | Старт новой фичи / завершение фичи / смена направления |
| 🧊 COLD | `docs/contracts.md`, `docs/log.md`, `memory/ic_roadmap.md`, `memory/plugin_architecture.md`, `CONCEPT.md` | Архитектурное решение / новая мажорная версия / явный запрос |

---

## Правила

### 1. Старт сессии — только HOT

Claude читает при старте **только** `HANDOFF.md` и `memory/MEMORY.md` (индекс).
Остальные документы — по запросу, когда задача явно требует.

Исключение: если пользователь открывает сессию с конкретной задачей из backlog —
читается также соответствующий WARM-документ.

### 2. Один факт — одно место

Каждый тип информации живёт ровно в одном документе.
Остальные могут содержать **ссылку**, но не копию.

| Тип информации | Единственный источник |
|----------------|-----------------------|
| Текущий статус проекта | `HANDOFF.md` |
| Детали задач | `docs/backlog.md` |
| Архитектурные решения | `docs/contracts.md` + `docs/log.md` |
| IC roadmap | `memory/ic_roadmap.md` |
| Demo план | `docs/DEMO.md` |

### 3. HANDOFF — строго one-pager

Максимум 20-25 строк значимого контента.
Структура:
- Текущий статус (2-3 строки)
- Активные задачи (3-5 строк)
- Находки последней сессии (3-5 строк)
- Следующая сессия (0-3 строки — только если есть триггер)

Детали задач — не в HANDOFF, а в `backlog.md` по ID.
Архитектурные обоснования — не в HANDOFF, а в `contracts.md` или `log.md`.

### 4. Обновление в конце сессии

После каждой сессии обновить:
- `HANDOFF.md` — «Находки последней сессии» + статус + поле «Следующая сессия»

При завершении фичи / смене направления (WARM-триггер) дополнительно:
- `docs/backlog.md` — пометить задачу ✅, проверить соответствие реальности
- WARM memory-файл активной фичи — если были решения
- Все WARM-документы прочитать и проверить на drift: если устарели — обновить на месте

COLD-документы обновляются только при явном архитектурном изменении.

### 4а. Поле «Следующая сессия» в HANDOFF

Триггер заполнения: команда «обнови handoff» / «осталось 5%».

Алгоритм:
- Явно нет триггера → поле не пишем, идём дальше
- Явно есть конкретный триггер → пишем, сообщаем пользователю
- Непонятно → задаём вопрос

Примеры WARM-триггеров: начало новой фичи, завершение фичи, смена приоритета, счётчик.
Примеры COLD-триггеров: архитектурное решение, изменение контракта агента.

### 4б. Страховочный счётчик WARM

В HANDOFF хранится строка: `Сессий с последнего WARM-ревью: N (порог: 5)`

При каждом «обнови handoff» Claude инкрементирует N.
При N ≥ 5 → добавляет в «Следующая сессия»: *WARM-ревью (счётчик)*.
После WARM-ревью → счётчик сбрасывается в 0.

Назначение: страховка для нелинейного маршрута — когда явных событий нет,
а документы всё равно могут дрейфовать.

### 5. Не создавать, если есть где записать

Перед созданием нового документа или memory-файла — проверить,
нет ли уже подходящего места. Новый файл оправдан только если тип информации
не покрыт существующей структурой.

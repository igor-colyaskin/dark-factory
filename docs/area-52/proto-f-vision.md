# Area 52 — Proto-F: Aviation Factory Vision

> Area 51 = отложенные идеи для DF-IC.
> Area 52 = стратегический горизонт: от самолёта к авиазаводу.

**Статус:** vision, облачный замок. Первый шаг не определён.
**Дата:** 2026-05-13

---

## Метафора

DF-IC — самолёт, собранный в ангаре. Цель — авиазавод (proto-F),
который производит разные самолёты серийно.

---

## Ключевые решения (сессия 2026-05-13)

### 1. DF-IC не трогаем

Пусть летает. Берём из него чертежи (паттерны, structure),
но не рефакторим под платформу.

### 2. Два параллельных продукта

Строить DF-A и DF-B одновременно, чтобы увидеть настоящий шов
между общим и специфичным. Без второго потребителя — абстракция
преждевременна.

Выбранные кандидаты (решение 2026-05-13):
- **DF-C** (Columnist) — генератор news-обозревателей (News API + LLM summarization)
  - Роль: основной demo-продукт для EPAM/публичного показа
  - Live demo: "при вас создаём NYTimes Sport обозревателя за 3 минуты"
  - Pipeline: order → architect (источник, тема, фильтры) → developer (Node app) → preview
  - API: newsapi.org (бесплатный tier, 100 req/day)
- **DF-T** (Telegram basic bot) — генератор простых телеграм-ботов
  - Роль: "на стапелях" — scaffold + skeleton, показывает масштаб конвейера
  - На демо: 15 сек, "вот следующий в очереди"
  - Технически: решает деплой + Telegram API — фундамент для DF-A и DF-TG

### Demo драматургия (три акта)

1. **DF-IC** — "уже в продакшене, летает" (скриншот, 30 сек)
2. **DF-C** — "сейчас при вас соберём" (live demo, 3-5 мин)
3. **DF-T** — "следующий на стапелях" (scaffold, 15 сек)

Сообщение зрителю: это конвейер, не одноразовая поделка.

### 3. Структура репозитория

```
proto-f/
  CLAUDE.md              <- общие правила для всех фабрик
  memory/                <- обобщённые инсайты
  playbook/              <- паттерны pipeline, verify, prompts
  shared/                <- только utility (LLM-обёртка, fs helpers)
  forge/
    df-a/CLAUDE.md       <- специфика продукта A
    df-b/CLAUDE.md       <- специфика продукта B
```

`shared/` на старте минимален (LLM client, retry).
Архитектурные блоки (orchestrator, UI, registry) живут копиями
в каждой forge/df-x/ до момента extract.

### 4. Контракт с первого дня

Каждый плагин общается с ядром через единый JSON-интерфейс:

```javascript
module.exports = {
  name: 'columnist',
  prompts: { architect, developer },
  verify: (output) => result,
  generateStatic: (slug, spec) => files
}
```

Ядро вызывает `profile.prompts.architect(input)` —
не знает и не должно знать, что за контрактом.

### 5. Composable agents (горизонт)

За контрактом может скрываться:
- Один LLM call (Gemini анализирует мокап)
- Team (TL + BE + FE за одним интерфейсом)
- Внутренняя DF (фабрика для фабрик)

Вызывающая сторона не меняется. JSON in -> JSON out.
Как Unix pipe: не важно, cat или сложный awk — интерфейс один.

### 6. Аккумуляция опыта

Опыт завода = knowledge для агента, не код:
- **CLAUDE.md иерархия** (proto-f/ -> forge/df-x/)
- **Memory** на уровне proto-f (обобщённые инсайты)
- **Playbook** (формализованные рецепты: как pipeline, как verify)
- **Decision log** на мета-уровне

RAG / MCP — overkill на текущем масштабе. Файловая система +
Claude Read/Grep = достаточная платформа. Пересмотреть при 5+ фабриках.

## Дорожная карта продуктов

Каждый шаг добавляет один новый технический элемент:

```
DF-IC  → уже летает (SAP, production)
DF-C   → News API + stateless preview       [первый]  публичное демо, EPAM
DF-T   → Telegram API + деплой              [второй]  решает инфраструктуру
DF-A   → автономные каналы + scheduler      [третий]  строится на DF-T
DF-TG  → игры + state + multi-player        [четвёртый] строится на DF-T/DF-A
```

DF-TG (Telegram-игры: шахматы, нарды, Мафия) — интересная идея,
но требует деплоя + persistent state + multi-user session.
Реалистична только после DF-T, когда инфраструктура решена.

---

## Что НЕ делаем

- Не проектируем shared/core/ заранее — extract после двух живых примеров
- Не строим microservices (HTTP между компонентами) — module interface достаточен
- Не трогаем DF-IC ради архитектурной чистоты
- Не строим RAG/MCP пока масштаб не требует

## Контекст аудиторий

- **SAP:** DF-IC закрывает основные болезненные места. Второй SAP-продукт не приоритет.
- **EPAM:** стимулируют обучение/применение AI, но практического приложения для DF нет.
  DF-C — демо AI-factory подхода для широкой аудитории.
- **Общее демо:** три акта показывают систему (завод), не единичный артефакт (самолёт).

**Приоритет:** средний — **до демо** (~2 ч)

### [TPL-004] protocol + viewControl как ортогональные измерения → шаблоны по протоколу
**Источник:** стратегическое обсуждение 2026-05-10 (финальное решение)
**Суть:** `spec.protocol` и `spec.viewControl` независимы. Шаблон выбирается по протоколу,
View адаптируется по viewControl. Никаких form-odata2, filter-odata2 и т.д.

**Архитектура:**
- `spec.protocol` — `"rest"` | `"odata2"` | `"odata4"` | `"other"` — **всегда спрашивать явно**, никогда не выводить автоматически
- `spec.viewControl` — конкретный UI5-класс (`"sap.m.Table"`, `"sap.m.SimpleForm"`, etc.) — выводить из структуры данных, спрашивать если неясно
- `spec.layout` — **удалить** (заменён на viewControl)

**Два шаблона по протоколу:**
- `template-rest/` (был `form-rest/`) — oCard.request() + DataHelper + DataEngine; extension point: `_processData()`
- `template-odata2/` (был `table-odata2/`) — ODataModel + metadataLoaded() + MockServer.simulate(); extension point: `_bindView()`

Developer выбирает шаблон по `spec.protocol`, заполняет View.xml + extension point по `spec.viewControl`.

**Что делать:**
1. Переименовать `templates/form-rest/` → `templates/template-rest/`, `templates/table-odata2/` → `templates/template-odata2/`
2. `template-odata2/`: заменить `_bindTable()` на обобщённый `_bindView()` stub
3. `architect.js` — убрать `layout`, добавить `viewControl`; протокол — обязательный явный вопрос
4. `developer.js` — выбор шаблона по protocol, адаптация View + extension point по viewControl; убрать layout-conditional
5. `contracts.md` — обновить IC spec fields
**Приоритет:** высокий — **до демо** (~3-4 ч)

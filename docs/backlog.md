### [TPL-002] Конвенция namespace / имя папки для IC карточек
**Источник:** устное обсуждение, сессия 2026-05-09  
**Суть:** При ручном изготовлении карточек название папки должно соответствовать namespace —
это занимает много времени и почти всегда содержит ошибки. В CARDS.md нет единой конвенции.  
**Что делать:**
1. Проанализировать CARDS.md — найти доминирующую тенденцию (namespace → slug)
2. Зафиксировать конвенцию в `docs/contracts.md` / системном промпте Архитектора
3. Если в заказе не указан slug — Архитектор выводит его самостоятельно из описания,
   показывает в Spec Review; пользователь корректирует если не нравится (не спрашивает явно)  
**Приоритет:** средний (обязательно до активного использования)

### [UX-002] Режим редактирования существующей карточки
**Источник:** устное обсуждение, сессия 2026-05-09  
**Суть:** Реальный рабочий режим: разработчик переключается между несколькими карточками,
вносит инкрементальные изменения ("перекрась кнопку", "добавь диалог").
Каждый раз создавать новый GitHub repo — неприемлемо.  
**Нужно:**
1. **Реестр карточек** — slug → GitHub repo URL. Открытый вопрос: где хранить?
   - `cards-registry.json` локально в DF (просто, но machine-specific)
   - Отдельный GitHub репо-индекс (portable, сложнее)
   - Пользователь вводит URL вручную (минимум реализации)
2. **Pull → workspace** — клонировать/обновить существующий repo
3. **Delta-промпт** — Архитектор видит текущие файлы + задачу изменения (не полный spec с нуля)
4. **Push без создания repo** — в существующий repo, не `git init / create`  
**MVP-гипотеза:** пользователь выбирает slug из реестра (или вводит GitHub URL) →
DF тянет repo → пайплайн с контекстом существующих файлов → push в тот же repo.  
**Приоритет:** высокий (блокирует реальное использование при >2 карточках)  
**Версия:** v0.12 (после v0.11 Smart input)

## Классификация модулей (e / s / c)

Гипотетическое разделение модулей по классам сложности:

- **e-class (elementary):** без связи с внешним миром. Пример: Local Runner.
- **s-class (simple):** требует API-ключ/токен. Пример: Developer agent, GitHub Client.
- **c-class (composite):** несколько s-class модулей, обёрнутых вместе. Пример: Developer Team.

**Статус:** описательная таксономия, не предписательная. Не меняет архитектуру
и дизайн. Может стать полезной после 3-4 реализованных модулей — когда будут
реальные примеры для каждого класса. До того — overhead без payoff.

## AI-driven apps

Идея: DF генерирует приложения, которые сами используют AI (LLM API).

**Открытые вопросы (без ответов):**
- Чей API-ключ в сгенерированном приложении? Пользователя? Захардкоженный?
- Как обрабатывать лимиты и стоимость?
- Как тестировать такие приложения в mock-режиме?

**Триггер для перевода в ROADMAP:** появление конкретного запроса от
"заказчика" (себя из будущего) на приложение, которому нужен LLM.

## Что после REMEMBER — направления

Потенциальные модули/возможности, которые могут вырасти из опыта
использования v0.5:

- **Iterator** — цикл "сгенерировал → проверил → поправил". Сейчас
  pipeline линейный. Триггер: когда качество генерации начнёт раздражать.
- **Variant Generator** — "сделай 3 варианта, я выберу". Триггер:
  одиночный результат перестанет устраивать.
- **Upgrader** — "возьми приложение из REMEMBER, обнови/доработай".
  Первый реальный потребитель REMEMBER.

**Принцип:** четвёртый модуль для "оглянуться и увидеть паттерны"
появится сам. Не надо его выбирать заранее.
